## 章ごとのメモ

### 第1章 データベースを制する者はシステムを制す

#### 学び・気づき

- RDB は今でも業務システムの中心的な選択肢だが、世の中のデータベースはそれだけではない。OODB、KVS、ドキュメントDB、階層型DBのように、それぞれ別の強みに寄せたモデルがあると整理できた。
- OODB は「プログラムのオブジェクトをそのまま保存したい」という発想のDBで、考え方自体は面白いが、今は主流というよりニッチな立ち位置だと分かった。発想の一部は ORM やドキュメントDB 側に受け継がれていると考えると理解しやすい。
- KVS は「キーで高速に取り出すこと」に特化したDBで、RDB でも主キー検索はできるが、用途を絞ることで単純さや速度、スケールしやすさを得ているのが本質だと分かった。
- セッション管理の例で考えると、RDB でも保存はできるが、セッションは高頻度アクセス・期限切れ・単純参照が中心なので、TTL を持てる Redis や Valkey のような KVS と相性がよい。ログイン状態の継続と、セッション本体をどこに置くかは別の話だと整理できた。
- ドキュメントDB は JSON のまとまりをそのまま保存したいときに向いていて、柔軟な構造やネストを扱いやすい。一方で、厳密な整合性や複雑なリレーション、集計が重要な領域では RDB の方が自然だと感じた。
- 階層型DB は親子関係の木構造を扱うモデルで、歴史的には重要だが、現代の一般的な新規開発では主役ではないと分かった。今でも一部の基幹系では使われているが、かなり限定的な領域の技術という印象。
- DOA（Data Oriented Approach）は処理ではなくデータ構造を中心に設計する考え方で、POA（Process Oriented Approach）は業務処理の流れを中心に組み立てる考え方だと理解した。長く保守する前提では、変わりやすい処理より比較的安定したデータを軸に考える DOA の重要性が大きい。
- 3層スキーマモデルは、外部スキーマ=利用者ごとの見え方、概念スキーマ=DB 全体の論理設計、内部スキーマ=物理的な保存方法、という分離の考え方だと分かった。見る都合・業務上の意味・保存の都合を混ぜないことが、設計の崩れにくさにつながる。

#### メモ

- RDB 以外のDBを「代替」ではなく「何に最適化したモデルか」で比較すると理解しやすい
- OODB は今の主流ではないが、「オブジェクトとDBのズレを減らしたい」という問題意識は今でも重要
- KVS は「RDB にできないこと」ではなく、「RDB でもできる単純アクセスを特化して得意にしたもの」と捉える
- セッション管理のように、厳密な関係管理より高速アクセスと期限管理が大事なデータは KVS の具体例として覚えておきたい
- ドキュメントDB は 1 件のまとまりで完結するデータ、RDB は複数の事実を正確に結びつけたいデータ、という見分け方を意識したい
- DOA と 3層スキーマモデルは、DB 設計を単なる保存先の話ではなく、システム全体の設計原則として見るための土台になりそう

### 第6章 データベースとパフォーマンス

#### 学び・気づき

- SQLは「何が欲しいか」は書けても、「どう取るか」はDBMS側の判断に委ねられている。だから性能改善では、SQLだけでなく実行計画やインデックス設計まで見る必要があると感じた。
- インデックスはコードを書き換えずに効く改善策になりうる一方で、雑に増やせばよいものでもない。検索条件と並び順に合わせて、必要なものだけを設計する意識が大事そう。
- B-treeは仕組みを細かく暗記するより、「範囲検索やソートと相性が良いのでよく使う」と理解しておくと、実務での判断に結びつけやすそうだった。
- カーディナリティやデータ件数の話を見て、インデックスはテーブルの大きさや値の散らばり方まで含めて考える必要があると分かった。
- 否定条件や列への演算のように、インデックスが効きにくい書き方がある点は特に意識しておきたい。
- 実行方法の選択はオプティマイザが担っていて、その判断材料として統計情報を参照する。SQLを書いたら終わりではなく、オプティマイザが選びやすい状態を作ることも大事だと感じた。
- 統計情報は古ければよい判断ができない一方で、収集自体は重い処理なので、更新タイミングや収集対象を絞る運用設計が重要になる。更新されていないテーブルまで毎回取り直す必要はない。
- 統計情報を新しくすると実行計画まで変わってしまうことがあり、場合によってはそれで性能が悪化することもある。安定稼働を優先して統計情報を凍結する、という考え方があるのは面白かった。
- パフォーマンス改善はインデックスだけではなく、ヒント句で実行計画を誘導する方法や、パーティションテーブル、パラレルクエリ、オンメモリーのような別方向の手段もあると分かった。

#### メモ

- インデックスを追加するか迷ったときに読み返したい
- 範囲検索や `ORDER BY` が遅いSQLを見て、B-treeで改善できそうか判断したいときに読み返したい
- 実行計画を見ても、なぜそのアクセス方法になるのか腹落ちしないときに読み返したい
- 否定条件や列への演算を書いたSQLで、なぜインデックスが効かないのか確認したくなったら読み返したい
- 統計情報の更新タイミングや収集範囲をどう決めるべきか迷ったときに読み返したい
- 実行計画を変えたくない場面で、統計情報の凍結やヒント句のような介入が必要か考えるときに読み返したい
- インデックス以外にどんなチューニング手段があるか、選択肢を思い出したいときに読み返したい

## 感想・雑記 (Thoughts)

- 第1章では、RDB 以外のデータベースも「何を得意にするか」という観点で整理すると理解しやすいと感じた。KVS やドキュメントDB は RDB の単純な代替ではなく、用途に応じて設計思想そのものが異なる。
- 特に KVS は、RDB でも実現できる単純なキー検索を、より高速かつ単純な形で扱うための選択肢だと整理できた。セッション管理のような具体例と結びつけて考えると、向いている場面がイメージしやすかった。
- DOA や 3 層スキーマモデルの話を通じて、DB 設計は保存方式の話に閉じず、システム全体の見通しや変更容易性を支える基盤なのだとあらためて認識した。
- 第6章は、DB設計の話から「実際にどう速くするか」へ視点が移る章としてちょうどよかった。
- まだ自分の理解は入口段階だけど、インデックスを用語として覚えるより「どんなSQLで効くか」を結びつけて読むほうが身につきそう。
- オプティマイザに任せる世界と、人間が統計情報やヒント句で介入する世界の境目が見えてきて、かなり面白かった。

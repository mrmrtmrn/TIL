## MySQLのインデックス追加とオンラインDDL運用

### 学んだこと

- 既存テーブルへのインデックス追加は読み取り性能改善に効く一方で、`INSERT` / `UPDATE` / `DELETE` の更新コストを増やすため、書き込み性能への影響を必ず見積もる
- インデックス追加時はロック影響を前提にし、本番では実行タイミングと同時実行トランザクションの状態を含めて計画する
- インデックスは「検索条件・結合条件で本当に使う列」に絞って設計し、過剰付与を避ける
- オンラインDDLは有効なダウンタイム低減手段だが、完全なロックゼロではなくメタデータロック（MDL）は必要
- MDLは主に「開始時の準備」と「終了時の定義反映」で短時間発生し、重いインデックス構築処理時間の全体をロックし続けるわけではない
- 長時間トランザクションが存在すると、オンラインDDLでも開始時・終了時のMDL取得待ちが発生しやすく、実運用では特に注意が必要
- MySQLはDBMS全体、InnoDBはその中のストレージエンジンであり、責務（管理基盤と保存実装）を分けて理解すると整理しやすい
- インデックス容量はケース差が大きく、データ量比で小さく収まる場合もあれば同等以上まで増える場合もあるため、概算だけでなく実測確認が重要

### オンラインDDLの理解を整理したメモ

オンラインDDLの挙動は、以下の3フェーズで捉えると理解しやすい。

1. 準備フェーズ
   - DDL開始に必要な整合性確保のため、短時間のメタデータロックを取得する
2. 実行フェーズ
   - インデックス構築などの重い処理を進める（多くのケースでDML継続が可能）
3. コミット/定義更新フェーズ
   - 最後に再度メタデータロックを取得し、定義反映を安全に切り替える

ポイントは「オンライン = 完全無停止」ではなく、「停止時間や影響を小さくする方式」という理解。

### インデックスサイズの実測で使うSQL

```sql
SELECT
  table_name,
  ROUND(data_length / 1024 / 1024, 2) AS data_size_mb,
  ROUND(index_length / 1024 / 1024, 2) AS index_size_mb,
  ROUND(index_length / NULLIF(data_length, 0), 2) AS index_to_data_ratio
FROM information_schema.tables
WHERE table_schema = 'your_database_name'
ORDER BY index_length DESC;
```

補足:

- `INDEX_LENGTH` でテーブル単位のインデックス領域サイズを確認できる
- `DATA_LENGTH` と並べると、サイズ比率で優先的に見直すテーブルを判断しやすい
- `SHOW TABLE STATUS` でもインデックス関連サイズを確認可能

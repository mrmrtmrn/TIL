## HTTPS/TLSハンドシェイクと証明書チェーンの理解整理

### 学んだこと

- HTTPS通信は大きく「TCP接続の確立 → TLSハンドシェイク → 暗号化されたHTTP通信」の順で進む
- TLSハンドシェイクの主目的は、(1) サーバー真正性の確認、(2) 利用暗号スイートの合意、(3) セッションで使う共通鍵の安全な共有
- 通信全体を公開鍵暗号で処理するのではなく、公開鍵暗号は主に鍵共有の安全化に使い、実データは高速な共通鍵暗号で暗号化する
- サーバー証明書の信頼判定はクライアント側で実施され、OS/ブラウザが持つ信頼済みルート証明書ストアを起点にチェーン検証する
- 証明書検証では「CA署名の連鎖」だけでなく、ドメイン一致・有効期限・失効状態・用途（Key Usage/Extended Key Usage）なども確認する
- 証明書の役割は分離して捉えると分かりやすい（ルート証明書: 信頼の起点 / 中間証明書: 発行実務の中継 / サーバー証明書: 対象サービスを識別）
- 証明書自体は公開情報であり、秘密にすべきは秘密鍵。秘密鍵はアクセス制御やHSMなどで厳格に保護する
- ハンドシェイク中に証明書検証が行われ、検証成功後に鍵共有が成立してから共通鍵暗号通信に移行する
- 共通鍵はセッション単位で一時的に使われ、接続終了やタイムアウトで破棄されるため、同時接続が多い環境でもセッション単位で管理される

### 概念の整理メモ

#### 証明書チェーン検証の流れ

1. サーバーがサーバー証明書（必要に応じて中間証明書チェーンを含む）を提示
2. クライアントが署名をたどってルートまで検証
3. 到達したルート証明書がローカル信頼ストアに存在するか確認
4. 追加検証（FQDN一致・有効期限・失効・用途制約）を通過したら信頼

#### 鍵共有と暗号化通信の流れ（理解用）

1. クライアントが接続を開始
2. サーバーが証明書を提示
3. クライアントが証明書を検証
4. 鍵交換処理でセッション鍵を共有
5. 以降のアプリケーションデータを共通鍵で暗号化して送受信

### 実機確認で使えるコマンド例

```bash
curl -vI https://www.google.com
```

補足:

- `-v` でTLS接続時の詳細ログを確認できる
- 証明書関連情報（発行者や検証結果の一部）をCLIで素早く把握できる
- より詳細な証明書内容は OpenSSL コマンドでの展開確認が有効

# AI Session Notes - 2026-04-12

## CRUD と常時接続の違い

### 学んだこと

- CRUD は HTTP の典型的なリクエスト/レスポンス型で、1 回の処理が終わると通信は基本的に完了する
- 常時接続は WebSocket のように接続を維持し続け、必要なタイミングで双方向にメッセージを送る
- 一般的な Web アプリの多くは CRUD が中心で、チャット・対戦ゲーム・共同編集などは常時接続の性質が強い
- 「アクセス数が多い」と「大量の接続を長時間維持する」は別問題であり、後者では接続維持コストが重要になる

### 詳細

CRUD は「必要なときだけ問い合わせる」形で、一覧表示・作成・更新・削除などの業務処理に向く。一方で WebSocket は「つないだまま待つ」形なので、通知・チャット・リアルタイム同期のような即時配信に向く。

## Rails と Go の得意領域の違い

### 学んだこと

- Rails は認証、バリデーション、DB 操作、画面生成などがまとまっており、CRUD 中心の Web アプリを高速に作りやすい
- Go は goroutine を前提に、大量の接続維持やリアルタイム配信のような I/O 待ちの多い処理を比較的軽く扱いやすい
- 「通常の業務アプリは Rails、リアルタイム機能は Go」という補完関係になることがある
- Web アプリ全体を単一言語で完結させるより、負荷特性の違う部分だけ分離する方が合理的な場合がある

## Action Cable の向き不向き

### 学んだこと

- Rails には Action Cable があるため、リアルタイム機能を Rails に載せること自体は可能
- ただし Action Cable があるからといって、大量の常時接続を低コストで維持する用途まで常に最適とは限らない
- リアルタイム機能が補助的であれば Action Cable は十分有力だが、WebSocket が主役のサービスでは専用構成を検討する価値がある
- 判断基準は「接続数」「配信頻度」「低レイテンシ要求」「WebSocket が主役かどうか」

## Rails アプリに Go の WebSocket サーバーを混在させる構成

### 学んだこと

- 混在構成では、通常の HTTP/CRUD は Rails、WebSocket 接続は Go と入口から分けるのが自然
- すべての WebSocket メッセージを毎回 Rails が中継するのではなく、接続確立後は Go が直接さばく構成が一般的
- 認証の正本は Rails に置き、Go は Rails が発行した署名付き短命トークンや JWT を検証する形にすると分離しやすい
- 永続化や複雑な業務ルールは Rails 側に寄せ、Go は接続維持とブロードキャストに専念させる設計が扱いやすい
- イベント連携には Redis や Queue を使い、Rails が発行したイベントを Go が購読して配信する形がよくある

### 詳細

典型的な流れは次の通り。

1. ユーザーは Rails でログインする
2. Rails が画面と WebSocket 接続用のトークンを返す
3. ブラウザは Go の WebSocket サーバーに接続する
4. Rails が保存したイベントや状態変化を Redis / Queue へ流す
5. Go がそれを購読して接続中クライアントへ配信する

この構成にすると、Rails は業務ロジックと永続化、Go は大量接続の維持と即時配信という分担がしやすい。

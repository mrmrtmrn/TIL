# AI Session Notes - 2026-06-21

## EC2 直運用からコンテナ運用へ段階的に移行する考え方

### 学んだこと

- Go などで作ったシンプルな Web API を EC2 だけで動かす場合、仮想サーバー上にバイナリやランタイムを配置し、プロセス管理、ログ、セキュリティパッチ、デプロイ、障害復旧を自分で扱う必要がある。
- Docker を導入すると、アプリケーションの実行環境をコンテナイメージとして固定できるため、ローカル環境と本番環境の差分を減らしやすい。
- Amazon ECR はコンテナイメージの保管場所として使える。EC2 は成果物を直接持つ場所ではなく、ECR から image を pull して実行する場所として扱える。
- Amazon ECS を使うと、手動の `docker run` ではなく、タスク定義とサービスによって「どの image を、何個、どの設定で動かすか」を管理できる。
- ECS on EC2 ではコンテナの起動管理は ECS に任せられるが、コンテナを動かす EC2 インスタンスの台数、パッチ、キャパシティは引き続き管理対象になる。
- ECS + Fargate ではコンテナを動かす EC2 インスタンスを直接管理しなくてよくなる。CPU、メモリ、ポート、環境変数、ヘルスチェック、スケーリングなど、アプリケーション実行単位の設定に意識を寄せられる。
- Amazon EKS は Kubernetes を AWS 上で使うための選択肢。Kubernetes のエコシステムや社内標準が必要な場合には有力だが、シンプルな Web API の初期ステップとしては ECS より学習・運用コストが高くなりやすい。

### 詳細

シンプルな Web API を例にすると、インフラ作業の責任範囲は次のように変化する。

```text
EC2 のみ:
  EC2 に SSH して、Go バイナリやランタイムを配置して起動する。
  systemd などで常駐化し、OS やプロセスを自分で管理する。

EC2 + Docker:
  アプリを Docker image に固め、EC2 上では Docker container として起動する。
  実行環境の再現性は上がるが、EC2 と Docker daemon の管理は残る。

EC2 + Docker + ECR:
  image を ECR に push し、EC2 から pull して起動する。
  成果物の置き場と実行場所を分離できる。

ECS on EC2:
  ECS の Task Definition と Service でコンテナの起動・維持を管理する。
  コンテナが落ちた場合の再起動や複数台への配置を ECS に任せられる。

ECS + Fargate:
  コンテナ実行基盤の EC2 管理を手放し、コンテナ単位で CPU・メモリ・台数を指定して運用する。
  EC2 直運用からのステップアップとして理解しやすい。

EKS:
  Kubernetes の Deployment、Service、Ingress などでコンテナを運用する。
  強力だが、Kubernetes を使う明確な理由がある場合に選ぶ方がよい。
```

最初の学習ルートとしては、EC2 に直接アプリを置く運用から始め、次に Docker 化し、ECR に image を置き、最終的に ECS + Fargate で動かす流れが理解しやすい。各段階で「何を自分で管理し、何を AWS に任せるのか」が見えやすくなる。

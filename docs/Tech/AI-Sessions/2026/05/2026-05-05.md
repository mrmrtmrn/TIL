# AI Session Notes - 2026-05-05

## Go の main 関数で依存を組み立てる考え方

### 学んだこと

- Go ではアプリケーションの入口で repository、service、handler などの部品を明示的に組み立てることが多い。
- `main` は業務ロジックの詳細を持つ場所ではなく、どの実装を使い、どの順番で依存を渡すかを決める composition root として扱える。
- Rails のようにフレームワークや ActiveRecord の規約が依存関係を隠す設計とは異なり、Go では依存を明示することで差し替えやテストをしやすくする。
- 規模が大きくなった場合も、依存関係はどこかで組み立てる必要がある。ただし `main.go` にすべてを書くのではなく、`app` や `bootstrap` のような組み立て専用の層へ移すことがある。

### 詳細

小さなアプリケーションでは、入口で次のように依存を渡していく形が分かりやすい。

```go
repo := NewRepository()
service := NewService(repo)
handler := NewHandler(service)
```

この形では、service が repository を自分で作らない。service は「保存先の具体的な実装」を知らず、渡された依存を使うだけになる。

将来、保存先がメモリから DB に変わっても、service の責務を大きく変えずに repository 実装を差し替えやすい。

## Repository パターンの役割

### 学んだこと

- repository はデータの保存、取得、更新など、永続化や保存先とのやり取りを担当する部品として捉えられる。
- service はユースケースを担当し、handler は HTTP などの入出力を担当する。
- repository を service に注入すると、service は保存先がメモリなのか DB なのかを知らずに済む。

### 詳細

repository は、たとえば以下のような操作を受け持つ境界になる。

```go
List(ctx)
Create(ctx, value)
FindByID(ctx, id)
Update(ctx, value)
```

handler から repository を直接呼ばず service を挟むことで、HTTP の都合とユースケースの都合を分けやすくなる。

## Go の channel と select の基本

### 学んだこと

- channel は goroutine 同士で値を受け渡すための通り道。
- `ch <- value` は channel へ送信し、`value := <-ch` は channel から受信する。
- channel からの受信は、値が届くまで待つ。
- `select` は複数の channel 操作を同時に待ち、先に進めるようになった `case` を 1 つ実行する構文。
- `select` はすべての channel を待つ AND 条件ではなく、どれか 1 つが起きれば進む OR 条件として読める。

### 詳細

複数の終了条件やイベントを待つ場合、`select` を使うと「先に起きた方」に反応できる。

```go
select {
case err := <-errCh:
    // サーバー起動処理などが error を返した
case <-ctx.Done():
    // context がキャンセルされた
}
```

この例では、`errCh` に値が来なくても `ctx.Done()` が反応すれば `select` は進む。両方が完了するまで待つわけではない。

## Go の context はキャンセルやタイムアウトを伝える

### 学んだこと

- Go の `context` は、処理にキャンセル、締切、リクエスト単位の情報を伝えるためによく使われる。
- Web API、DB アクセス、外部 API 呼び出し、goroutine を扱うコードでは `context.Context` が頻繁に登場する。
- HTTP リクエストでは `r.Context()` を service や repository に渡すことで、クライアント切断やタイムアウトを下位層へ伝えられる。
- `signal.NotifyContext` を使うと、Ctrl+C や SIGTERM などの OS signal を context のキャンセルとして扱える。
- `defer cancel()` や `defer stop()` は、context に関連する後始末を関数終了時に実行するための予約としてよく使われる。

### 詳細

アプリケーション終了時の signal を context として扱うと、メイン処理は `ctx.Done()` を待つことで終了要求を検知できる。

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

select {
case <-ctx.Done():
    // 終了 signal を受け取った
}
```

`defer` は、現在の関数が終わる直前に処理を実行するための構文。`stop` は `signal.NotifyContext` が返す関数で、signal の監視を解除するために使う。

    AI Session Notes - 2026-04-06

    Google Cloud Load Balancer 配下の WordPress で HTTPS ループを防ぐ

    学んだこと

    • Cloud Armor は Compute Engine 単体へ直接付けるのではなく、External Application Load Balancer の backend service に適用する構成が基本になる
    • Load Balancer で TLS を終端する場合、HTTP -> HTTPS リダイレクトの責務はアプリではなく Load Balancer 側へ寄せると構成が安定しやすい
    • siteurl / home は https:// のまま維持し、WordPress 側の「HTTP なら HTTPS に飛ばす」処理だけを外すのがよい
    • Load Balancer からオリジンへの通信が HTTP でも、X-Forwarded-Proto: https を見て WordPress に HTTPS 扱いさせれば、無限リダイレクトや管理画面の誤動作を防ぎやすい
    • siteurl / home を http:// に変えると、WordPress が http ベースの URL を生成しやすくなり、無駄なリダイレクトや mixed content の原因になりやすい

    詳細

    Load Balancer で TLS を終端し、バックエンドへは HTTP で転送する構成では、オリジン側から見ると「HTTP で来た」ように見えることがある。この状態で WordPress 側の HTTPS 強制リダイレクトを残していると、外からは常に https:// でアクセスしているのに、オリジンが毎回「HTTP だから HTTPS に飛ばそう」と判断し、ループが発生しやすい。

    この問題を避ける典型的な補正が X-Forwarded-Proto である。Load Balancer が付与した X-Forwarded-Proto: https を見て、アプリ側で HTTPS とみなす。

    if (isset($_SERVER['HTTP_X_FORWARDED_PROTO']) && $_SERVER['HTTP_X_FORWARDED_PROTO'] === 'https') {
    $_SERVER['HTTPS'] = 'on';
}

    この補正を入れた上で、HTTP -> HTTPS リダイレクトは Load Balancer 側に一本化すると、責務が分離されて見通しがよくなる。

    Google-managed certificate を前提にした役割分担

    学んだこと

    • self-managed certificate を Load Balancer に載せた場合、オリジンサーバー上の Let's Encrypt 更新とは自動同期されない
    • 長期運用では、TLS 終端を担う Load Balancer 側で Google-managed certificate を使うほうが自然で、更新運用も簡潔になる
    • Google-managed certificate の発行と更新は、対象ドメインの A / AAAA レコードが Load Balancer の forwarding rule の IP のみを向いていることが重要になる
    • GeoDNS や第三者 CDN の影響で、認証局から見た到達性や名前解決が不安定だと、証明書の発行や更新に失敗することがある
    • Compute Engine を引き続きインターネットへ直接公開すると Cloud Armor をバイパスされるため、移行後は Load Balancer と health check 以外からの到達を閉じる必要がある

    詳細

    Google-managed certificate は Load Balancer 側で自動更新されるため、サーバー側で Let's Encrypt を回し続ける必要がなくなる。一方で、発行・更新の条件として、認証局が複数地点からドメインの名前解決と到達性を確認できる必要がある。DNS が Load Balancer 以外の IP を返したり、途中にプロキシや CDN が入っていたりすると失敗しやすい。

    そのため、最終構成では次の分担がわかりやすい。

    • Load Balancer: TLS 終端、HTTP -> HTTPS リダイレクト、Cloud Armor
    • オリジン: HTTP:80 でアプリを返す、X-Forwarded-Proto による HTTPS 判定補正

    参考手順: Global External Application Load Balancer + Google-managed certificate + Cloud Armor

    手順の前提

    • 既存構成は Compute Engine 1台 + Nginx + WordPress
    • 既存の HTTPS はオリジン上の証明書で終端している
    • 新構成は Global External Application Load Balancer -> Cloud Armor -> Compute Engine
    • バックエンド通信はまず HTTP:80 を使う
    • 作業は Google Cloud Console ベースで行う

    事前準備

    1. WordPress の siteurl / home が https:// であることを確認する
    2. wp-config.php に X-Forwarded-Proto 対応を追加する
    3. WordPress 側の HTTPS 強制リダイレクトを外す
    4. Nginx に 200 OK を返すヘルスチェック用パスを追加する
    5. DNS の TTL を短めに調整する

    画面遷移ベースの作業順

    1. Compute Engine -> Instance groups で既存 VM を含む unmanaged instance group を作成する
    2. 同じ画面で named port http:80 を設定する
    3. Network services -> Load balancing -> Health checks で HTTP ヘルスチェックを作成し、パスに /lb-healthz を設定する
    4. VPC network -> Firewall で health check 用の許可ルールを追加し、35.191.0.0/16 と 130.211.0.0/22 からの tcp:80 を許可する
    5. VPC network -> IP addresses で Global の静的外部 IP を予約する
    6. Security -> Certificate Manager の Classic Certificates から Google-managed certificate を作成し、対象ドメインを登録する
    7. Network services -> Load balancing で Application Load Balancer (HTTP/HTTPS) を新規作成する
    8. 種別は Public facing (external)、Best for global workloads、Global external Application Load Balancer を選ぶ
    9. Backend configuration で instance group を backend に設定し、protocol は HTTP、health check には作成済みの /lb-healthz を選ぶ
    10. Frontend configuration で HTTPS:443 を作成し、予約済みの静的グローバル IP と Google-managed certificate を関連付ける
    11. 同画面で HTTP to HTTPS redirect を有効化し、80 -> 443 のリダイレクトを Load Balancer に担当させる
    12. Security -> Cloud Armor で backend security policy を作成する
    13. 最初は OWASP CRS 3.3 系の preconfigured WAF rules を preview で適用し、必要に応じて /xmlrpc.php deny や /wp-login.php rate limit を足す
    14. Load balancing の backend service 編集画面から Cloud Armor policy を関連付ける
    15. backend が Healthy であることを確認し、WordPress 管理画面でリダイレクトループや mixed content が起きないことを確認する
    16. DNS の A / AAAA レコードを Load Balancer の静的 IP に切り替える
    17. Google-managed certificate の状態が ACTIVE になったことを確認する
    18. 動作確認後、Cloud Armor の preview ルールを段階的に enforce に寄せる
    19. 最後に、オリジンの 443 直公開と不要になった証明書更新運用を整理し、Load Balancer と health check 以外からの到達を閉じる

    切替後の確認項目

    • http:// でアクセスしたときに Load Balancer 側で https:// へリダイレクトされる
    • https:// で証明書エラーが出ない
    • WordPress のログイン、管理画面、投稿、画像表示でループや mixed content が出ない
    • Cloud Armor のログで誤検知が多発していない
    • Compute Engine へ直接入る経路が残っておらず、Cloud Armor をバイパスできない
